# Architecture (deep dive)

Full architectural reference for the PHP SDK.

> **What this file is for — and what it deliberately omits.** It records what the code cannot: the alternative that was considered and rejected, the failure mode each decision prevents, and the empirical result behind it. The **class inventory** — which class extends which, which method lives where, what a constant contains — is derivable from `src/` in a couple of greps and is **not duplicated here**, because a prose copy of the code drifts out of true while the code cannot. This file has twice had to correct its own claims about the code: see the RSRMID-2923 correction under the interface-constructor entry, and the "primitives remain abstract" docblock error under the pagination entry. Read `src/` for structure; read this for _why_.
>
> CLAUDE.md carries a trip-wire pointing here, not a summary of these entries. Every decision below names its **guard test**. A green suite is not evidence a decision still holds — most of these refactors are behaviour-preserving the day they land, which is why the guards are structural.

## Shape of the tree

`CNIC\` maps to `src/` (PSR-4), with `CNR`/`IBS`/`MONIKER` sub-namespaces. Each brand supplies a `Client`, `SocketConfig`, `Response`, `ResponseParser`, `ResponseTranslator`, `ResponseTemplateManager` and `Logger`; the shared abstracts (`AbstractClient`, `AbstractSocketConfig`, `AbstractResponse`, `AbstractResponseTemplateManager`, `AbstractResponseTranslator`), the shared concretes (`Record`, `Column`, `HttpTransport`, `ApiDateTime`) and the interfaces sit in `CNIC\`. Read the inheritance chain and the member lists off `src/` directly. The facts about the tree that are **decisions** rather than structure:

- **The brands are siblings, not parent/child.** `CNR\Response` and `IBS\Response` both extend `AbstractResponse`; neither is-a the other. IBS previously extended `CNR\Response`/`CNR\Record` directly and threw `UnsupportedFeatureException` from 5 inherited CNR-only methods — a refused-bequest smell removed in RSRMID-2904 by pulling the shared machinery up into `AbstractResponse`/`AbstractRecord` and segregating the interface. RSRMID-2923 then found that the sibling _Record_ pair, and most of the sibling _Column_ pair, had no differences left to carry. `MONIKER\Client extends IBS\Client` because they are the same API platform — only the `SocketConfig` differs — and it is deliberately **not** `final` (see the RSRMID-2920 entry). MONIKER has no `Response` of its own; it reuses IBS's.
- **Response construction is a template method.** `AbstractResponse::__construct()` is the skeleton and delegates the brand-specific steps to protected hooks — `translate()` (raw-response translation), `populate()` (parse + record assembly), `newRecord()` (record factory) and `newResponseParser()` (parser factory), each marked `#[\Override]` in the brands. When adding a brand or changing how a response is parsed, implement the hooks; **never reimplement the constructor.** Its shape is load-bearing — the parser-seam entry below deliberately added a *sixth* such dispatch rather than opening the constructor up.
- **Placeholder stripping is per-field, not global.** `AbstractResponseTranslator` strips `{UPPER}` placeholders through a per-field callback that runs only inside the human-readable field (`description` for CNR, `message` for IBS), so `{UPPER}` content in other data fields survives. A global strip corrupts data fields. (Ref: RSRMID-2893.)

## Decision records

- **The pagination seam is deliberately asymmetric — derived getters on the base, primitives per brand (do not "simplify" it):** `AbstractResponse` implements the 5 getters that are pure functions of the primitives (`getNextPageNumber`/`getNumberOfPages`/`getPagination`/`getPreviousPageNumber`/`getRecordsCount`) and leaves the 7 primitives (`getCurrentPageNumber`/`getFirstRecordIndex`/`getLastRecordIndex`/`getRecordsTotalCount`/`getRecordsLimitation`/`hasNextPage`/`hasPreviousPage`) to each brand. RSRMID-2912 proposed hoisting single-page defaults for the 7 onto the base and deleting IBS's overrides; it was **declined** and is now closed as **Cancelled** (deliberately not "Done" — the refactor was never implemented, and a Done record would assert the opposite of what shipped). **This entry is therefore the authoritative decision record**, not the Jira issue: it is the reason the rationale below is written out in full here rather than left in a ticket. RSRMID-2918 is the live issue that corrected the docblock and added the guard.
  - **The premise it was built on was wrong.** The old class docblock claimed the primitives "remain abstract here", which reads as *`AbstractResponse` declares them `abstract`*. It does not — the only members it declares abstract are the three protected hooks `translate()`/`populate()`/`newRecord()`. The 7 are plain `ResponseInterface` methods the base simply never implements; reflection reports them as abstract members of `AbstractResponse` purely because it implements that interface, with `getDeclaringClass()` still pointing at `ResponseInterface`. The docblock was corrected in RSRMID-2918 so the same refactor is not proposed again off the back of it. Two corollaries, since RSRMID-2918 itself asserted otherwise and the mistake is easy to repeat: (a) "not abstract" is true only in the sense that matters — `AbstractResponse` declares nothing, though the methods *are* abstract by virtue of the interface, which is why reflection lists them; (b) `addColumn` is **not** wrongly grouped with them — it is in exactly the same category (interface-declared, unimplemented on the base, supplied per brand at `src/CNR/Response.php` / `src/IBS/Response.php`), so do not "fix" the docblock by removing it from that list. What separates `addColumn` and the status/code accessors from the 7 primitives is only that the no-defaults rule below is specific to pagination.
  - **Failure mode the seam prevents: a silent wrong answer.** Today a brand that forgets pagination cannot be instantiated — PHP raises a declaration-time fatal for the unimplemented interface methods. With base defaults it would instead quietly report "page 1 of 1, no next page", and a consumer paging a list would lose pages 2..N with no error anywhere. Trading a loud compile-time error for a silent data-loss default is the wrong direction, and the saving was 6 one-line bodies — not the ~60 lines the ticket claimed, since most of IBS's block is the load-bearing `getLastRecordIndex()` docblock plus its real `count - 1`-or-`null` logic (the fix for a `LAST = -1` underflow on empty lists).
  - **A `SinglePageResponse` trait was also rejected**, despite the `CNR\SessionCapable` precedent for traits in this codebase: there are only two Response implementations (MONIKER reuses `IBS\Response` verbatim), so any base default *or* trait would serve exactly one consumer — speculative generality. Revisit only if a third genuinely non-paginating brand arrives.
  - **Erosion is CI-guarded, and only reflection can do it.** `tests/ResponsePaginationSeamTest.php` asserts each brand declares all 7 itself, that the base's declaration of them still belongs to `ResponseInterface`, and that the 5 derived getters *are* on the base. A structural test is not a stylistic choice here: the refactor is behaviour-preserving (base defaults would return exactly what IBS returns today), so no behavioural test can detect it. Verified by doing it — with a `getCurrentPageNumber()` default hoisted onto the base and IBS's override deleted, the seam test failed (2 of its 3 methods) while the **entire rest of the suite stayed green**: 339 passed, 0 failed. If you repeat that experiment, note that `.github/phpunit.xml` sets `stopOnDefect="true"`, so a plain `composer test` halts at the first failure and leaves the rest pending — to observe the "nothing else fails" half you must run the suite with the seam test temporarily set aside (or flip that flag). (Ref: RSRMID-2912 declined, RSRMID-2918.)
- **Record/column construction is factory-hooked, but the two use opposite hook shapes because the types allow only that:** `AbstractResponse::addRecord()` delegates to an abstract protected `newRecord(array $h): RecordInterface` **output** hook — each brand implements it to build its Record. Records work as an output factory because both brands share one shape (`array<string,mixed>`); since RSRMID-2923 both hooks return the same shared `CNIC\Record`. Columns **cannot** use that shape: a CNR column takes `string[]` while an IBS column takes mixed JSON values, so a param-typed `newColumn(string, array): ColumnInterface` factory can't stay type-clean under PHPStan L9 / Psalm L1 — the base factory would have to narrow `array<array-key,mixed>` into CNR's `string`-bound constructor, which both analysers reject (`argument.type` / `MixedArgumentTypeCoercion`) and the toolchain forbids silencing. The bookkeeping is instead de-duplicated the **other way round**: each brand's `addColumn()` builds its own correctly-typed Column locally and hands the finished instance to a shared `AbstractResponse::registerColumn(ColumnInterface $col): static` helper that owns the `$columns`/`$columnkeys`/`$columnindex` bookkeeping once. So the input to the shared step is polymorphic (a constructed column), not a param-typed factory. Don't try to "symmetrise" columns onto a `newColumn()` factory like records — it is infeasible under strict analysis; keep the `registerColumn()` shape. Note that RSRMID-2923 did **not** change this: sharing a column *base* is a different question from a param-typed *factory*, and the constructor value types still diverge — which is precisely why the shared column is templated instead. (Ref: RSRMID-2899, superseding the RSRMID-2898 note that left `addColumn()` fully duplicated; RSRMID-2923 for the shared types.)
- **The record/column layer is collapsed to one class each — do not re-split it per brand (RSRMID-2923, breaking, v25.0.0).** This layer had five classes where two sufficed: `AbstractRecord` plus two byte-identical empty subclasses, and two independent `Column` implementations duplicating ~35 lines (the length field, the constructor, `getKey()`, `getData()`) with three trivial differences — a `@param` annotation, the `getDataByIndex()` return type, and whether the bounds check was extracted into a helper or inlined. It was the last place in the Response layer where the shared-base pattern used for Client, SocketConfig, Response, TemplateManager and Translator was not applied.
  - **What landed:** one concrete `CNIC\Record` (the abstract and both markers gone) and one concrete, templated `CNIC\Column`. `CNR\Column` is the only surviving brand column and declares exactly one method — `getDataByIndex(): ?string` — earning its place by binding `TValue` to `string`. `IBS\Column` is gone; IBS/Moniker instantiate the shared column directly.
  - **The analyser question the ticket made a precondition, answered empirically:** a covariant `?string` override against the base's `mixed` return is accepted by **both** PHPStan L9 and Psalm L1, and needs no suppression. The templated `@extends CNIC\Column<string>` binding is genuinely enforced rather than decorative — `new CNR\Column("X", [1, 2, 3])` is rejected by both (`argument.type` / `InvalidArgument`). This is a net **loss** of one suppression: the hand-rolled `CNR\Column` carried `@psalm-suppress MoreSpecificImplementedParamType` for narrowing the interface's constructor param, which the template makes unnecessary.
  - **`newRecord()` stays an abstract per-brand hook** even though both brands now return the same class. That is deliberate: the hook is the seam a brand with genuinely different row behaviour would implement, and hard-coding `new Record()` on the base would close it. The two three-line bodies are the price of keeping the seam open, and are not the pass-through smell this ticket deleted — an empty `class Record extends AbstractRecord {}` carried no decision, whereas the hook body *is* the brand's declaration of its record type.
  - **Erosion is CI-guarded, and only reflection can do it.** `tests/RecordColumnSeamTest.php` asserts no brand namespace owns a `Record`, that no `IBS\Column` exists, that the shared classes stay concrete and own the shared body, that both `newRecord()` hooks return `CNIC\Record`, and that `CNR\Column` declares nothing but `getDataByIndex()` with a `?string` return. Re-adding an empty marker or re-inlining the shared body is behaviour-preserving the day it lands, so no behavioural test could catch it. Both mutations were run and confirmed to fail the seam test (and only it).
  - **Coverage was a side effect worth naming.** `tests/CNR/ColumnTest.php` was 18 lines with a single `testGetKey()` — `getData()`, `getDataByIndex()` and the bounds behaviour had no direct CNR coverage at all, while the IBS equivalent had eight tests. The shared behaviour is now covered once in `tests/ColumnTest.php`/`tests/RecordTest.php` for both brands, and the brand test classes were re-pointed at what is actually brand-specific: the `addColumn()`/`newRecord()` wiring and CNR's narrowed return type.
- **The parse step is a seam, not a static call (RSRMID-2924, breaking, v26.0.0).** `populate()` called `RP::parse($this->raw)` (CNR) / `RP::parse($this->raw, $this->command)` (IBS) — static, hard-wired, and with **different signatures**, so no shared contract was even expressible. The consequence was testability: nothing in the Response tree could be exercised without a full raw wire payload, and the CNR parser had no test file at all. `CNIC\ResponseParserInterface` now declares one signature, `parse(string $raw, array $cmd = []): array`, and both brand parsers are instantiable classes implementing it.
  - **The shape is the `TransportInterface` one, deliberately.** An abstract `newResponseParser()` factory hook supplies the brand default (twin of `newRecord()` / `AbstractClient::newTransport()`), and the constructor takes an optional last argument `?ResponseParserInterface $parser = null` that overrides it. Adding an *optional* parameter is legal widening, so no implementation stops satisfying anything — and, per the RSRMID-2923 correction above, no interface declares a constructor any more, so there is nothing to keep in step. `populate()` reads `$this->parser`; a brand that writes `new RP()` inline instead compiles, behaves identically and silently closes the seam, which is why the guard is structural.
  - **CNR takes `$cmd` and ignores it, on purpose.** The alternative — a contract covering only IBS's shape, or two contracts — buys nothing: CNR's wire format is self-describing, and a uniform signature is what makes one seam serve both brands. `populate()` feeds both the same way, asserted by `ResponseParserSeamTest::testCNRAlsoReceivesTheCommandEvenThoughItsParserIgnoresIt()`.
  - **The template manager's `parseResponse()` hook is gone**, replaced by the same `newResponseParser()`, so a brand names its parser once per class rather than repeating the call. It still parses with **no** command — a template is not tied to one — while `Response::populate()` passes the command it was built with. For IBS that selects the JSON branch versus the plain-text branch; both reach the same hash for template text (the JSON branch falls back to plain text), which is now **asserted** in `IBS\ResponseTemplateManagerTest` and `IBS\ResponseParserTest` rather than left as an invisible divergence. Note which pair those tests compare: the divergent input is a command **without** `ResponseFormat`, since a command carrying `ResponseFormat=JSON` takes the *same* branch as the empty one and would make the assertion vacuous — the first draft of both tests did exactly that and had to be rewritten.
  - **One type consequence worth knowing.** Behind the interface the hash is `array<string, mixed>`, so CNR's `populate()` no longer reads the string-list shape of `PROPERTY` off the concrete parser's return type. It re-establishes it in `CNR\Response::stringCells()` — a private narrowing step that rejects nothing for a real CNR response (the wire format is textual, which is also why `CNR\Column` binds `TValue` to `string`). A non-string cell — **and equally a column entry that is not a list** — **throws** `UnsupportedFeatureException` naming the column: skipping would be the silent no-op RSRMID-2919/RSRMID-2920 ruled out, and coercing would invent a value the wire could never carry; both are unreachable with either brand parser and a programming error from a substitute. The container check is the half that is easy to forget, and this change shipped without it for one review round: the first draft wrote `foreach ((array)$values …)`, which turned a bare string into a one-cell column while a bare `int` still threw one line later — coercing a bad container while refusing a bad cell, in a method whose docblock claimed it did neither. Deliberately asymmetric with the level above it: a **missing or non-array `PROPERTY` block** still yields no columns rather than throwing, exactly as the `is_array()` guard it replaced did, because most CNR responses legitimately have none. Written as a loop with one `@psalm-suppress MixedAssignment` because PHPStan narrows `array_filter(…, "is_string")` and Psalm does not; the shared `AbstractResponse::getHashArray()` helper (twin of `getHashString()`) supplies the block.
  - **`AbstractResponseTemplateManager::resetTemplates()` came along in the same pass** (additive). `$templates` is public static state with process lifetime and had no way back, so a template registered by one test class was visible to every later one in the same process — and a long-lived consumer registering per request accumulated them forever. The built-ins are captured per concrete class on that class' first `addTemplate()`, so the reset is per brand and a no-op when nothing was registered. Its reach is stated on the method rather than implied: it is `addTemplate()`'s counterpart, not a general undo, and a **direct assignment to the public `$templates` property escapes it** — the RSRMID-2921 lesson that a guard on one writer does not protect state with several. Closing that writer means making the property non-public, which `CNR\ResponseTranslator::templates()` reads across a class boundary; that is a separate change, not silently assumed away here.
  - **What this deliberately did not do.** The ticket also observed that `AbstractResponse::__construct()` dispatches into subclass territory before the object is finished, "so a response cannot be built and then populated for a test". The seam **adds a sixth** such dispatch (`newResponseParser()`) rather than removing any: the ticket's own proposed change was injection, and injection makes the parse step substitutable without touching the constructor's shape — which is load-bearing (see the template-method bullet above). Build-then-populate remains impossible by design; if that ever becomes the requirement, it is a different ticket about the constructor, not about parsing.
  - **Erosion is CI-guarded, in both halves.** `tests/ResponseParserSeamTest.php` proves behaviourally that a substitute (`CNICTEST\Support\SpyResponseParser`, the parser twin of `SpyTransport`) reaches the hash through the public constructor with no reflection and no subclass, and structurally that `parse()` stays a non-static two-parameter method, that both brands declare the factory hook, and that no second parse route exists on the manager. The structural half is unavoidable: with `populate()` mutated back to `(new RP())->parse(…)` every other test in the suite — 495 of them, i.e. all but this file — stays green, and only the seam test refuses it. The direct parser tests moved to `tests/<Brand>/ResponseParserTest.php`; the 16 nominal parser tests that lived in `tests/IBS/ResponseTest.php` are there now, with the CNR ones written from scratch.
- **The logger seam is at the format, not the sink (RSRMID-2925, breaking, v27.0.0).** `LoggerInterface` was one method, `log(): void`, and both implementations ended in `echo`. The seam therefore sat where nothing varied — the destination was standard output for every brand — while the part that does vary (CNR joins command, POST body, error and plain response with newlines; IBS emits a labelled REQUEST/RESPONSE block with tab indentation) returned nothing and could only be observed by capturing output. The contract is now two halves: `format(string $post, ResponseInterface $r, ?string $error = null): string` on `LoggerInterface`, and `CNIC\LogSinkInterface::write(string): void` for the destination. `CNIC\AbstractLogger` holds the sink (defaulting to the shipped `CNIC\EchoSink`), implements `log()` as `sink->write(format(…))` and leaves `format()` abstract; both brand loggers are `final` and declare `format()` only.
  - **`AbstractLogger::log()` is `final`, and that is the load-bearing part.** A subclass reintroducing `log()` is behaviour-identical under the default echo sink and silently ignores an injected one — the same shape as a brand writing `new RP()` inline and closing the parser seam. Making it final turns that from an invisible regression into a declaration-time fatal.
  - **`setDefaultLogger()` was replaced by the protected `newLogger(LogSinkInterface $sink): LoggerInterface` hook**, the twin of `newTransport()`/`newSocketConfig()`/`newResponseParser()`, plus a public `AbstractClient::setLogSink()`. Without the hook the only way to choose a destination would be `setCustomLogger(new CNIC\CNR\Logger($sink))` — naming a brand concrete at the call site, which is exactly what this project tells integrators not to do. `setLogSink()` rebuilds the brand logger around the sink, so it also discards a previously set custom logger; that is stated on the method, in README and MIGRATION, and pinned in both directions by `LoggerSeamTest::testSetLogSinkReplacesAPreviouslySetCustomLoggerAndNotTheReverse()` rather than left to be discovered. The two seams deliberately do **not** compose through the client — a custom logger's destination is its own business, and a `LoggerInterface` has no sink slot to write into — so last call wins and the order is documented.
  - **A sink was preferred over a second logger interface** because two real implementations justify it immediately (`EchoSink` for the demo apps and the default, `CNICTEST\Support\CollectingSink` for tests) and because it is what gives the WHMCS/Blesta bundles the brand's format for free — previously an integrator routing debug output to a file had to reimplement the format from scratch. Note what the sink deliberately does *not* get: the response. A PSR-3 adapter wanting a severity level derived from the response status writes a `LoggerInterface` implementation, not a sink; handing the response to both halves would make the split meaningless.
  - **Masking is unaffected, and was re-verified rather than assumed.** Both inputs are already masked upstream — `AbstractResponse::sanitizeCommand()` masks the response's stored command, and `performRequest()` passes `getPOSTData($mycmd, true)` — so making the record obtainable widens where it can end up but not what it contains. Asserted per brand on the returned string, and note what the assertion has to be made *of*: the first draft handed the formatter a hand-written pre-masked `$post` literal, which passes with masking switched off entirely — the IBS format never renders `getCommand()`, so the POST body is its only secret-bearing input. Both brand tests now build that body through the real client (`getPOSTData($cmd, true)`), which is what makes the CNR test cover `PASSWORD`/`AUTH` and the IBS test cover `password`/`transferAuthInfo`; each was confirmed to fail with its brand's `$sensitiveFields` emptied.
  - **Coverage was a side effect worth naming**, the same one RSRMID-2923 found for columns: `CNR\Logger` had **no test at all** and IBS's nine tests all went through `ob_start()`. Both brands now assert their format on the returned string, with output buffering left only where the destination is the thing under test.
  - **Erosion is CI-guarded, in both halves.** `tests/LoggerSeamTest.php` asserts structurally that `format()` is declared on the *interface* and returns `string`, that neither brand declares `log()`, that `log()` stays final, and that no client re-grows `setDefaultLogger()`; behaviourally that an injected sink receives exactly what `format()` returned while nothing reaches output. The structural half is unavoidable: with `format()` dropped from the interface and left on the concrete loggers, every brand test keeps passing (they call the concrete class) while interface-typed consumers lose access to the string — verified by doing it, 519 tests green with only the seam test and the `LoggerTest` contract pin refusing it. The second mutation (un-`final` `log()`, re-add an echoing override on `CNR\Logger`) fails the seam test too.
- **Core vs. extended Response contract (interface segregation):** `ResponseInterface` is the **universal** contract every brand fully supports. The richer capabilities of the CNR-class API — telemetry (`getQueuetime()`/`getRuntime()`), transient/pending status (`isTmpError()`/`isPending()`) and the table-friendly `getListHash()` — live on `ExtendedResponseInterface extends ResponseInterface`, implemented **only** by `CNR\Response`. IBS/Moniker responses implement the core interface only, so those 5 methods are simply **absent** there (not present-and-throwing). `AbstractClient::request()` returns the core `ResponseInterface`; a consumer holding that shared type must narrow via `instanceof \CNIC\ExtendedResponseInterface` before calling any of the 5. Consumers holding the concrete `CNR\Client`/`CNR\Response` are unaffected — `CNR\Client::request()` returns the concrete `CNR\Response`, which has everything. Do **not** re-add the 5 to the core interface. (Ref: RSRMID-2904.)
- **An interface declaration must match its implementation, and must not describe construction (RSRMID-2918).** Two drifts had accumulated on `ResponseInterface`, both fixed in v20.0.0. They share one root cause — the interface was edited independently of the class implementing it — but they resolve in *opposite* directions, which is the instructive part:
  - **`getColumnKeys()` — widen the interface to match the implementation.** The interface declared `getColumnKeys(): array` while `AbstractResponse` has always implemented `getColumnKeys(bool $filterPaginationKeys = false): array`. Because this project mandates typing against the interface, the pagination-stripping capability was **unreachable to exactly the consumers told to depend on it**: the call ran fine, but PHPStan/Psalm rejected it with `Method CNIC\ResponseInterface::getColumnKeys() invoked with 1 parameter, 0 required`, leaving only bad workarounds (retype to `CNR\Response` and lose brand-neutrality, or silence the analyser). Widening the interface is **breaking** for direct implementers (they must add the parameter), hence the major bump; callers are unaffected because `false` is the default. General rule: when a parameter is added to an implemented method, add it to the interface **in the same change**.
  - **`__construct()` — delete it from the interface instead.** It declared 3 parameters (`$raw, $cmd, $ph`) against `AbstractResponse`'s 4 (`$context` was added for custom loggers). Syncing it would have been the wrong fix: nothing constructs through the interface — responses are built by the brand factory hooks `AbstractClient::newResponse()` and `AbstractResponseTemplateManager::createResponse()`, each instantiating its own concrete `Response`. So construction is already the factories' concern and the interface is the wrong place to describe it; what remains is a contract about what a response can be *asked*. Removal only relaxes the contract, so no implementation stops satisfying it — verified: instantiating via `class-string<ResponseInterface>` with 3 or 4 args analyses identically before and after. The single externally observable effect is reflective: `(new ReflectionClass(ResponseInterface::class))->getConstructor()` now returns `null`.
    - **Two factual corrections to this entry, both made in RSRMID-2923 by running the code rather than reasoning about it.** As originally written it claimed "PHP **exempts constructors from signature-compatibility checks**, so the declaration constrained no implementer — which is precisely why this drift could persist silently". Both halves are wrong, and the error matters because it is the stated justification for a "do NOT" directive and would be cited again. (a) PHP exempts constructors only in **class-to-class inheritance**; a constructor declared on an **interface** is fully enforced, and an incompatible implementation is a declaration-time fatal (`Declaration of Rogue::__construct(int $a) must be compatible with Ifc::__construct(string $key, array $data)`). So the declaration *did* constrain every implementer. (b) The drift persisted for an unrelated and much more mundane reason: `$context` is an **optional** parameter, and adding an optional parameter is legal widening under LSP — `__construct(string $raw, array $cmd = [], array $ph = [], array $context = [])` satisfies a 3-parameter interface declaration without complaint. The **decision** is unaffected — removal still stands on the design ground above — but the mechanism is the opposite of what was recorded, and "an interface constructor is unenforced" must not be repeated. Lesson worth generalising: this entry asserted a language rule from memory; one 10-line script settled it.
  - **Extended to the whole layer in RSRMID-2923.** `ColumnInterface` and `RecordInterface` still declared `__construct(string $key, array $data)` and `__construct(array $data)` respectively — the last two instances of the pattern. Both are now gone, on the same design ground (nothing constructs through either type: columns come from a brand's `addColumn()`, records from its `newRecord()`, both naming concrete classes) and with the added weight that, per the correction above, the declaration was genuinely enforced and so genuinely limiting — it ruled out any column not born from a plain `(key, array)` pair, and it was what forced the old hand-rolled `CNR\Column` to carry `@psalm-suppress MoreSpecificImplementedParamType`. Removal is a **relaxation**, so it is non-breaking and needed no major bump of its own; it rode the v25.0.0 change because it is the same layer and the same decision. Guarded by `RecordColumnSeamTest::testNeitherInterfaceDeclaresAConstructor()`, verified non-vacuous by re-adding the declaration and watching it fail. Note the surviving `@psalm-suppress MoreSpecificImplementedParamType` on `CNR\Response::addColumn()` is **not** the same thing and must stay — it is about the interface's `addColumn()` parameter, an ordinary method, which was confirmed by deleting it and watching Psalm flag it.
  - **Both are guarded by `tests/ResponseInterfaceConsumerTest.php`, and neither could be guarded behaviourally** — the same lesson as the pagination seam above. For `getColumnKeys()` the test makes its calls on `ResponseInterface`-typed variables, so PHPStan L9 / Psalm L1 (which analyse `tests/`) fail `composer lint` if the signature narrows again; before the fix the interface was wrong and all 342 tests passed. For `__construct()` the guard is a reflection assertion, because PHP will never flag a re-add. To find this defect class again, compare `getNumberOfParameters()` of every interface method against each implementation — a throwaway reflection script over `src/`'s interfaces surfaced both in seconds.
- **Transport tuning is the caller's decision, not a brand default (RSRMID-2915, breaking in v20.0.0).** `IBS\Client` used to override `getDefaultCurlOpts()` to return `[CURLOPT_IPRESOLVE => CURL_IPRESOLVE_V4]`, forcing IPv4 name resolution on every IBS/Moniker integration. It was a workaround for a handful of customers whose hosts misbehaved over IPv6, and the library has since been shown to work without it. The override is removed: one environment's networking problem is the wrong thing to hard-code into everyone's transport, and picking a resolution mode is a caller concern. Affected integrations opt in with `setExtraCurlOptions([CURLOPT_IPRESOLVE => CURL_IPRESOLVE_V4])` — the public API added in RSRMID-2913, which was deliberately the first step of this cleanup so the escape hatch existed before the default was withdrawn.
  - The `getDefaultCurlOpts()` hook itself **stays**, even with zero overrides: `resetCurlOptions()` is defined in terms of it (restoring defaults rather than blindly wiping the bag), and a genuinely protocol-mandatory option could still justify one. A default that merely papers over one environment's networking does not — do not re-add one. It moved from `AbstractClient` to `AbstractSocketConfig` with the option bag in RSRMID-2921, so the guard moved too: `ClientConfigSeamTest::testNoBrandOverridesTheDefaultCurlOptsHook()` asserts all three brand **configs** resolve it to `AbstractSocketConfig`, and `testClientsHaveNoCurlOptionDefaultHook()` asserts no client offers a second one.
  - Note the consequence for migrating callers: an opted-in option is *caller* state, so `resetCurlOptions()` discards it and it must be set again — whereas before, IPv4 survived a reset as a brand default.
- **The caller wins on cURL options, except on a closed set the transport owns — and rejection is loud (RSRMID-2919, breaking in v21.0.0).** `setExtraCurlOptions()` used to be a half-truth: the value landed in the client's `$curlopts` bag (so introspection and the unit tests looked right) and was then dropped one layer down, because `HttpTransport::post()` did `curl_setopt_array($h, [transport defaults] + $options)` and PHP's `+` keeps the **left** operand on a duplicate key. Eleven keys never reached the wire — a caller asking for a 5s timeout silently got 300s. The operands are now swapped (`$options + [defaults]`), so the caller wins, and the keys that must not be caller-controlled are rejected instead of ignored.
  - **Why not simply swap the operands.** The 11 colliding keys were three different things, and only one of them was a defect. *Envelope invariants* — `CURLOPT_URL`, `POST`, `POSTFIELDS`, `RETURNTRANSFER`, `HEADER` — must stay unoverridable or response parsing breaks (`RETURNTRANSFER => 0` makes `curl_exec()` return `true` and the parser gets nothing). *Security posture* — `SSL_VERIFYPEER`/`SSL_VERIFYHOST` — was protected only by accident, but the protection is real and worth keeping deliberately: a generic convenience bag is the wrong place to disable certificate verification. *Legitimate tuning* — `TIMEOUT`, `CONNECTTIMEOUT`, `HTTPHEADER`, `USERAGENT` — is where the actual bug was, and those are now caller-overridable.
  - **The protected set is `HttpTransport::PROTECTED_OPTIONS`** (public, so consumers and tests can read it) and passing any of them raises `UnsupportedFeatureException` naming the offending constants, before the handle is touched — a rejected option is a programming error, not a network event, and must not cost a request. Silence was the whole defect; do **not** downgrade this to an ignore. Pinned by `HttpTransportCurlOptionsTest::testProtectedOptionsAreExactlyTheEnvelopeAndTlsKeys()`: widening the list silently re-breaks legitimate tuning, narrowing it gives away one of the two guarantees, so either direction has to be a deliberate edit.
  - **`CURLOPT_HTTPHEADER` is additive, and the transport's own lines are protected too.** Caller lines are appended; restating one of the transport's four (`Expect:`, `Content-Type`, `Content-Length`, `Connection`) throws, matched case-insensitively on the field name. This is the header-level twin of `PROTECTED_OPTIONS` and follows from it: `Content-Type`/`Content-Length` are derived from the POST body and `Connection` from the reused handle, so overriding one corrupts the request exactly as overriding `CURLOPT_POSTFIELDS` would — and a wrong `Content-Length` fails *silently*, which is the defect class this ticket closed. Replacing wholesale would drop the transport's entries; appending blindly would put two `Content-Type` lines on the wire and leave the winner to the server; so a collision is an error rather than a merge. A non-array `CURLOPT_HTTPHEADER` is deliberately left in `$options` for cURL to reject with its own `TypeError` (verified: `curl_setopt_array()` raises before `curl_exec()`, so nothing is sent) — dropping it quietly would be the wrong lesson to draw from this ticket.
  - **The timeout gap is closed separately, and was additive:** `AbstractClient::setSocketTimeout()`/`getSocketTimeout()` delegate to `AbstractSocketConfig`. Before this there was **no** supported way to change the request timeout — the property is protected with only a getter, the SocketConfig had no public accessor on the client, and the `CURLOPT_TIMEOUT` route was the one being discarded. v21 left **both** routes working with the bag winning on collision, which took 22 lines of prose on the client to explain; **RSRMID-2921 closed the second route** (`CURLOPT_TIMEOUT` is in `MANAGED_OPTIONS` and now raises), so the setter is the only way in and the prose is gone. (Note for archaeologists: v20.0.0's docs briefly named a `setSocketTimeout()` that did not yet exist — corrected in `1838c76`, then made true here.)
  - **A negative timeout is rejected at the setter,** via the new `CNIC\Exception\InvalidConfigurationException` (additive, extends `CnicException`, so `catch (\Exception)` consumers are unaffected). Not gold-plating: verified on PHP 8.3.31 that `curl_setopt($h, CURLOPT_TIMEOUT, -5)` returns `false`, and `HttpTransport` does not inspect `curl_setopt_array()`'s return, so a negative value would have been dropped with no signal — the same silent divergence, reintroduced by the very setter added to end it. The new exception type is for *configuration values out of range*, as distinct from `UnsupportedFeatureException` (capability absent); reuse it rather than reaching for a bare `\Exception` next time a setter needs a guard.
  - **The test that let this through is the lesson.** `AbstractClientCurlOptionsTest::testSetExtraCurlOptionsMergesOverTheBag()` asserted the bag and passed throughout, for two releases, while half the options it described were being discarded. Assertions about transport behaviour have to observe the *effective* arguments: `tests/HttpTransportCurlOptionsTest.php` covers the rejection guard offline, `tests/Functional/HttpTransportTest.php` proves the merge over a loopback socket (a stalling endpoint plus a 1s caller timeout — asserting the effect, not the option value), and `CNICTEST\Support\SpyTransport` records what the client hands the transport. "In the bag" is not "on the wire".
- **Client contract segregation (the client-tree twin of the Response one):** `AbstractClient` used to be a CNR base wearing a hat — `IBS\Client` overrode `getSession()`/`setSession()`/`setRoleCredentials()`/`useHighPerformanceConnectionSetup()` only to throw `UnsupportedFeatureException`, and no-opped `autoIDNConvert()` (a refused-bequest smell). RSRMID-2911 resolved it per-method rather than moving all four:
  - `useHighPerformanceConnectionSetup()` is **brand-agnostic** — it **stays on `AbstractClient`** and is available (opt-in) on IBS/Moniker too; the caller supplies the local proxy. (It was a scheme+host rewrite through `getURL()`/`setURL()` here; RSRMID-2921 made it a flag on the config so it stops costing the caller `isOTE()` — see the configuration-home bullet.)
  - `getSession()`/`setSession()` were kept **on `AbstractClient`** on the grounds that every brand's `SocketConfig` already implemented them (`AbstractSocketConfig` returned `""`/no-ops), making them "harmless" on IBS/Moniker. **This sub-decision was reversed in RSRMID-2920 — see the session-seam bullet below.** They now live on `CNR\Client`. (IBS's throwing overrides were deleted here and have not come back.)
  - `setRoleCredentials()` is **genuinely CNR-only**: it depends on the role separator, which is `""` on `AbstractSocketConfig`/IBS and only `":"` on CNR, so inheriting it on IBS would silently forge a garbage `<uid><role>` login. It moved onto **`RoleCredentialsInterface`** (in `CNIC\`, `@psalm-api`, single method), implemented only by `CNR\Client`, and was removed from the shared type. Consumers holding the shared `AbstractClient` narrow via `instanceof \CNIC\RoleCredentialsInterface` before calling it — exactly the `ExtendedResponseInterface` pattern. Do **not** re-add `setRoleCredentials()` to `AbstractClient`.
  - `autoIDNConvert()`'s IBS override was **redundant dead code**: `IBS\SocketConfig::$needsIDNConvert = false` already made the base method short-circuit and return the command verbatim. The override was deleted; a comment on the flag carried the intent. **This is the one method the per-method resolution got wrong** — it kept the CNR rules on the shared base and settled for a flag that disabled them, which is the same shape as the `setSession()` null objects two bullets above. RSRMID-2922 finished it: the flag is gone and the rules moved to `CNR\IDNCommandRewriter` — see the IDN bullet below. (Ref: RSRMID-2911, superseded by RSRMID-2922.)
- **The session seam is CNR-only, and absence is the chosen policy (RSRMID-2920, breaking, v22.0.0).** The config tree kept the half of the RSRMID-2911 split that the client tree had already cut. `AbstractSocketConfig` carried five CNR concepts as **null objects** — `getSession()` returned `""`, `setSession()`/`setPersistent()` returned `$this` unchanged, `getPersistent()` returned `false` — while `CNR\SocketConfig` re-declared `private $session`/`private $persistent` and overrode all of them. Session state therefore existed in two places, and because the setters are fluent, `ClientFactory::ibs()->setSession("SESSION-ABC")` looked accepted and was discarded (`getSession()` then reported `null`). On top of that the CNR-only `persistent=1` wire parameter was appended by the shared `getPOSTData()` for every brand, and `getRoleSeparator()` sat on the shared config with exactly one consumer — `CNR\Client::setRoleCredentials()`, itself already CNR-only. What changed:
  - The five accessors, `$session`, `$persistent` and `$roleSeparator` now exist **only** on `CNR\SocketConfig`; `persistent=1` is emitted by CNR's own `getPOSTDataParams()` (appended last, so the encoded body is byte-identical). `AbstractSocketConfig::getPOSTData()` is now purely the `http_build_query()` step and knows nothing brand-specific.
  - `getSession()`/`setSession()` moved from `AbstractClient` to `CNR\Client`, and the empty `IBS\SessionClient`/`MONIKER\SessionClient` were deleted. `MONIKER\Client` stayed **non-final** on purpose: Psalm's `ClassMustBeFinal` fired on it once nothing extended it, but that rule only ever fires on leaf classes, so `CNR\Client`/`IBS\Client` escape it purely because something inside the repo extends them — sealing one brand on that accident would make consumer extensibility differ per brand for an inexplicable reason. The issue is suppressed at the class with that rationale. A welcome side effect: deleting the `final` leaves removed the source of the `LessSpecificReturnStatement` false positive on the inherited fluent setters, so that `src/` suppression came out of `psalm.xml` (`findUnusedBaselineEntry` proved it dead).
  - `CNR\Client::getSocketConfig()` is the **single narrowing point** from the shared `AbstractSocketConfig` property type to `CNR\SocketConfig`. It exists because PHP typed properties are invariant — a subclass cannot re-declare `$socketConfig` with a narrower type, so the covariant `newSocketConfig()` factory cannot inform the property's type. It uses an `instanceof`-guard-with-throw (`UnsupportedFeatureException`), never `assert()`, per the factory bullet below; the guard is unreachable in practice. It was the protected `cnrConfig()` until RSRMID-2921 gave the base a public accessor; there is no alias, deliberately — two methods narrowing the same property would be two places to keep in step.
  - **The policy question this settled.** The project held two opposite answers for the same defect class — a capability the platform cannot honour. RSRMID-2911 chose *silence* (these no-ops, recorded as "harmless"); RSRMID-2919 chose *noise* for transport-owned cURL options (`UnsupportedFeatureException` "rather than being ignored"). An integrator learned which applied by testing. RSRMID-2920 picked a third answer available only here: **absence**. Nothing to call means a static-analysis error at the call site, which beats both a runtime throw and a silent discard. Prefer absence where the type system can express it; where a method must exist on the shared surface, throw (RSRMID-2919). Never no-op.
  - Guarded by `tests/ClientSessionSeamTest.php`. Absence cannot be tested behaviourally — calling a method that is gone is a fatal `Error` — so reflection is the only instrument that can catch the stubs creeping back up. That is exactly why they survived from v11 to v21.
- **Connection configuration has exactly one home, and two invariants keep it that way (RSRMID-2921, breaking, v23.0.0).** The state was split between `AbstractClient` (`$socketURL`, `$system`, the `$curlopts` bag) and `AbstractSocketConfig` (endpoints, timeout, credentials) with no invariant tying the copies together, and three defects followed directly. The root cause was structural rather than stylistic: **there was no accessor for `$socketConfig` anywhere on the client**, so every configuration value needed a hand-written forwarder or was unreachable from outside — which is why ~26 of them accumulated and why `AbstractClient` was the repo's highest-churn file (43 touches in 120 commits).
  - **The division of labour.** The config owns *the connection*: where to connect (`$url`, `$oteUrl`/`$liveUrl`, `$highPerformance`), how to authenticate (login/password; CNR's session on its own subclass), and how the transport should behave (`$socketTimeout`, `$proxy`, `$referer`, `$curlopts`). The client owns *client behaviour*: logger and `$debugMode`, `$context`, the transport instance, and the SDK's own identity (`VERSION`/`$ua` — kept on the client because semantic-release rewrites `VERSION` in that file, and the UA is built from it). `AbstractClient::getSocketConfig()` exposes the config once; `CNR\Client` overrides it covariantly to return `CNR\SocketConfig`.
  - **The three drifts, all reproducible at v22.0.0 (b3c20ff).** (1) `useOTESystem()->setURL($custom)` left `isOTE()` reporting `true` forever while requests went to `$custom`. (2) `getURL()` and `getLiveUrl()` answered from different objects. (3) `setProxy()` wrote a cURL bag key, so `resetCurlOptions()` dropped it. Regression tests in `tests/AbstractClientConfigDriftTest.php`.
  - **Invariant 1 — the system is derived, never stored.** `getSystem(): ?System` compares `$url` to the two endpoints. There is no flag left to contradict the URL, and the nullable return is the point: after `setURL("https://staging.example/")` there is no honest OT&E-or-LIVE answer, and reporting the last selection is exactly how drift 1 happened. This is the "derive one from the other" option the ticket offered, taken in the direction that keeps `setURL()` authoritative.
  - **Invariant 2 — a value the SDK models cannot also come from the cURL bag.** `AbstractSocketConfig::MANAGED_OPTIONS` (`CURLOPT_TIMEOUT`/`USERAGENT`/`PROXY`/`REFERER`) is rejected by `setExtraCurlOptions()` with `UnsupportedFeatureException` naming the owning setter. Each already has one, and a bag value silently outranked it on the wire while the getter kept reporting the setter's — RSRMID-2919's "in the bag is not on the wire" defect reappearing one layer up, so it gets the same answer: throw. Rejection is **eager** here (the config knows immediately) whereas `HttpTransport::PROTECTED_OPTIONS` is checked on the next request (the transport is injectable, and which options it owns is its own business). Options the SDK has no opinion about — `CONNECTTIMEOUT`, `IPRESOLVE`, `HTTPHEADER` — stay caller-owned and untouched. Pinned by `AbstractClientCurlOptionsTest::testManagedOptionsAreExactlyTheOnesWithTheirOwnSetter()`; widening the list takes away legitimate tuning, narrowing it re-opens a second home.
  - **High-performance routing became a flag rather than a URL rewrite,** because the eager rewrite was itself a drift: the loopback URL no longer matched the OT&E endpoint, so switching on high-performance mode silently cost the caller `isOTE()`. It is now applied inside `getURL()`, so the selected system survives it and it survives a later system switch (routing is *how* to reach the endpoint, not *which* one). Readable via `usesHighPerformanceConnectionSetup()`. It stays on `AbstractClient` as a forwarder — still brand-agnostic, per RSRMID-2911.
  - **The ~26 forwarders were deliberately kept**, against the ticket's "collapsing the ~26 forwards" option. They are the documented consumer surface (`$cl->useOTESystem()->setCredentials(...)` appears in the README, every example and every prior migration section), and deleting them would rewrite every integration to fix nothing: a forwarder is one home with one answer, and the DoD's invariant is "no configuration value readable from two places **with two possible answers**". What `getSocketConfig()` changes is that a *new* setting no longer needs one — the churn driver, not the churn already paid for. The alternative shape the ticket offered (absorb the config into the client) was rejected for the opposite reason: it would have cost the "configure without constructing a client" property that motivated the ticket.
  - **`getCurlOptions()` puts the dedicated proxy/referer state on the *left* of the union, and that is load-bearing rather than belt-and-braces.** `setExtraCurlOptions()` refusing those two keys is not the only thing writing `$curlopts`: `getDefaultCurlOpts()` seeds it via the constructor and `resetCurlOptions()` re-seeds it, neither passing the guard. A brand default of `CURLOPT_PROXY` — exactly the "protocol-mandatory option" that hook is kept for — would bring drift 3 back **inverted**: the getter reporting the setter's value while the request used the default. Pinned by `AbstractClientConfigDriftTest::testDedicatedProxyStateBeatsABrandDefaultOnTheWire()`, which writes out the brand subclass that does not yet exist. `AbstractClient::executeCurl()`'s third `$extraCurlOpts` parameter was **removed** for the same reason: nothing in the SDK ever passed it, and as an option route that skipped `MANAGED_OPTIONS` it was a way for a subclass to put a second answer behind `getProxy()`.
  - **One symptom the ticket listed was deliberately not addressed:** with debug mode on, `performRequest()` calls `getPOSTData()` a second time to build the masked log line. Left alone. It is not a second *home* — both calls read the same config and cannot disagree — and producing a masked variant genuinely requires a second pass over the parameters; the only ways round it are a `getPOSTDataPair()`-shaped API or masking the encoded string, and neither is worth a debug-only saving. The other three symptoms were fixed or pinned: `getUserAgent()` is a pure read, the timeout's second route is gone, and `setCredentials()`'s session-clearing invariant is documented on the method and pinned by a test (it is correct behaviour — `CNR\SessionCapable::reuseSession()` depends on the ordering — it was just stated nowhere).
  - **Erosion is CI-guarded, and only reflection can do it.** `tests/ClientConfigSeamTest.php` asserts no client in the tree declares any config-owned property, that the config declares them all, that every client config method has a counterpart on the config, and that writes through either route agree. A re-added client-side copy is behaviour-preserving on the day it lands — the copy agrees with the original until something writes one of them — so no behavioural test can see it arrive, only the drift it later causes. Same argument as the pagination and session seams.
  - **No new forwarder was added, on purpose.** A `getOTEUrl()` on the client (the twin of the pre-existing `getLiveUrl()`) was written and then removed: a change whose thesis is that a configuration value no longer needs a hand-written forwarder should not open with one, and `getSocketConfig()->getOTEUrl()` is the answer it provides. Same reasoning for `usesHighPerformanceConnectionSetup()`, which lives on the config only.
- **CNR IDN command rewriting is a module, not a base-class method behind a flag (RSRMID-2922, breaking, v24.0.0).** `AbstractClient::autoIDNConvert()` was the largest method in that class (37 body lines) and every line of it was CNR domain knowledge: which parameter names carry a domain name (`PARENTDOMAIN|NAMESERVER|NS|DNSZONE` with an optional index — `DOMAIN` deliberately absent, the API converts that one itself), that `OBJECTID` is a *pattern* parameter whose content depends on `OBJECTCLASS` (RSRTPM-3167), and that an already-ASCII value is left alone. It ran on a base shared with IBS and Moniker, switched on by `needsIDNConvert`, a config flag whose only job was to disable it for two brands out of three.
  - **The fix used a hook that already existed.** The rules moved to `CNIC\CNR\IDNCommandRewriter::rewrite(array $cmd): array` — a `final` class of static rules, the same shape as `CommandFormatter` — called from `CNR\Client::buildCommand()`, one of the two variation points `performRequest()` already provides. `performRequest()` lost its third step; no brand-detection replaced it, because the call site *is* the brand. Nothing was added to the shared tree to make this possible, which is the argument for it: when brand behaviour needs a flag on a shared class, the hook it should have used is usually already there.
  - **Order matters and is pinned.** The rewrite runs *after* `flattenCommand()` (the rules match wire keys like `NAMESERVER0`, not the caller's nested input) and rewrites values in place, so the priority sort survives it. `IDNCommandRewriterTest::testPreservesKeyOrder()` states that; the CNR cassettes prove the wire bytes are unchanged end to end.
  - **What stayed:** the public `AbstractClient::IDNConvert()` — converting a caller-supplied list of names is brand-agnostic, and it has been public API since v7.1.0, so removing it would break consumers for no gain. It is a one-line pass-through to the vendor `centralnic-reseller/idn-converter`, which the rewriter also calls. **What went, breaking:** the protected `autoIDNConvert()`, the `needsIDNConvert` property on all three configs, and the public `AbstractSocketConfig::getNeedsIDNConvert()`.
  - **The testability argument is the reason this was a ticket at all.** With no surface of its own the behaviour was only reachable through `ReflectionMethod::setAccessible()` on a factory-built client — two test files did exactly that. Where a test has to bypass the interface to reach the behaviour, the module is the wrong shape. The rules now have a direct test (10 cases, including both halves of the `OBJECTID`/`OBJECTCLASS` decision and the absent-`OBJECTCLASS` case, which the reflection tests never covered), the `ext-intl` skip sits on that test rather than gating a client test, and IBS's pass-through is asserted through a probe subclass exposing its own `buildCommand()` hook instead of reflecting into the base. A side effect worth noting: those two `setAccessible()` calls were the **only** thing triggering the `UnusedMethodCall` suppression for `tests/` in `psalm.xml`, so Psalm's own `UnusedIssueHandlerSuppression` flagged the entry as dead and it came out — the second time `findUnusedCode`'s bookkeeping has paid for itself here (see the `LessSpecificReturnStatement` note in that file).
  - **Erosion guard:** `tests/ClientIDNSeamTest.php` asserts that no client in the tree declares `autoIDNConvert()` and no config declares `needsIDNConvert`/`getNeedsIDNConvert()`; `tests/AbstractClientIDNTest.php` keeps the `IDNConvert()` coverage and nothing else. Structural by necessity, the same argument as the session and configuration seams: hoisting the rules back up behind a flag is behaviour-preserving the day it lands — CNR still converts, IBS still does not — so only reflection can refuse it. Note the split: reflection to *test* behaviour is the smell this ticket removed, reflection to *guard absence* is unavoidable, and the repo separates the two by file (`*SeamTest.php`) so the distinction stays legible.
- **Config-driven, and brand state stays on the brand config.** Each `SocketConfig` carries the API config as typed properties rather than the per-namespace `config.json` files this replaced; `$session`/`$persistent`/`$roleSeparator` are `CNR\SocketConfig`-only (see the session-seam entry).
- **Type-hint against the interface, not the concrete class** (`LoggerInterface` not `Logger`, `ResponseInterface` not `Response`). Narrow to `ExtendedResponseInterface` only for the 5 CNR-only Response capabilities, and to `RoleCredentialsInterface` only for CNR role credentials. Which class implements which is derivable from `src/`.
- **Edit the shared pipeline in the abstract, the brand differences in the hooks** — the brand `ResponseTemplateManager`/`ResponseTranslator` classes hold only per-brand data plus hooks. Do not reimplement a pipeline per brand.
- **`ClientFactory` exposes typed named constructors** — `cnr(): CNR\SessionClient`, `ibs(): IBS\Client`, `moniker(): MONIKER\Client` — not a string-dispatch `getClient(string): AbstractClient`. Each returns the concrete brand client fully typed, so brand-specific capabilities need **no** narrowing on the normal path. Only CNR has a `SessionClient` (the IBS/Moniker ones were empty and were deleted in RSRMID-2920). The old `Registrar` enum and `UnknownRegistrarException` were removed with `getClient()` — an unknown registrar is now impossible by construction. Where code *deliberately* holds the shared `AbstractClient` and reaches a brand-specific method, use an `instanceof`-guard-with-throw, **never `assert()`** — PHP compiles `assert()` out when `zend.assertions` is disabled, so it cannot carry a runtime guarantee. (The one-line `assert($r instanceof Response)` in each brand's `request()` is a different thing: a static-analysis hint about a return type the factory hook already guarantees, not a capability check.) (Ref: RSRMID-2911, superseding the v17.1.0/commit 5cea723 shared-`AbstractClient` return type.)
- **The request lifecycle is a template method, and `request()` is symmetric across brands.** The shared pipeline (build command → resolve URL → serialise POST → cURL → construct Response → optional debug log) lives once on `AbstractClient::performRequest()`; brands vary it through exactly **two hooks plus their config subtype** — `buildCommand()` (CNR flattens as-is, IBS injects `ResponseFormat=JSON`), `newResponse()`, and `newSocketConfig()`, where a brand-mandatory cURL option would now go since the bag moved to the config in RSRMID-2921. **No brand actually varies it** — IBS/Moniker's `CURLOPT_IPRESOLVE` seed was removed in RSRMID-2915, so every brand starts from an empty bag. Every SocketConfig configures the **host only**: CNR appends its default `api/call.cgi`, IBS/Moniker pass a per-operation `$path` (e.g. `Domain/Create`). The symmetry is deliberate — RSRMID-2909 **dropped** the earlier "CNR must never accept a per-request path" rule (RSRMID-2864) rather than preserving it. When adding a brand or changing parsing, implement the hooks; never reimplement `performRequest()`. (Ref: RSRMID-2909, superseding RSRMID-2864.)
- **Date/time values are parsed on demand, never rewritten into the response:** `CNIC\ApiDateTime` is a standalone, immutable, UTC-only value object — deliberately **not** a `\DateTimeInterface` — that turns the two shapes the APIs emit (`Y-m-d H:i:s` with an optional fractional part from CNR; `Y/m/d` from IBS/Moniker, e.g. `2030/07/17`) into one flat struct: `?int $ts`, `string $date`, `?string $dateTime`, `string $tz`, `string $raw` (the `tz` field structurally pinned to `"UTC"` by a private constructor). The class is still standalone and still never invoked during response construction — nothing is rewritten into the response — but `src/` now reaches it from exactly two opt-in accessors, `Record::getDateTimeByKey()`/`Column::getDateTimeByIndex()` (below); `getPlain()`/`getHash()`/`getListHash()` still return raw API strings, and the consumer still opts in at the point of display. The design carries these decisions:
  - **Opt-in parser, not a response transformation.** The original ticket proposed rewriting date columns in the hash responses into a nested `{original, localized}` structure. Rejected: it is a breaking change on every consumer and bakes a server-side timezone assumption into data. That was the original RSRMID-2318 call: additive parser instead — a minor bump, no `BREAKING CHANGE`, no MIGRATION.md entry.
  - **Parser, not formatter.** No `in($tz)`, no locale formatting, no `ext-intl` (which the WHMCS `castDate()` helper needed and which the SDK will not take on), and no view-layer markup helpers — `toHtml()`/`assetPath()` were dropped from the planned surface when localization was split out to RSRMID-2916. Consumers localize from `json_encode($dt->toArray())` or `new \DateTimeImmutable("@{$dt->ts}")`. The field names are a superset of WHMCS `castDate()`, so that integration can drop its private copy.
  - **Strict two-stage parse, because neither stage alone suffices** (verified on PHP 8.3.31). An anchored regex gate runs first, because `createFromFormat("!Y-m-d", "2026-7-1")` succeeds with *zero* warnings; then `createFromFormat()` in an explicit UTC `\DateTimeZone` (so the process default timezone cannot shift the instant), rejecting on **any** `getLastErrors()` warning — because PHP reports out-of-range components as a *warning* while still handing back a rolled-over object (`2026-13-45` → `2027-02-14`, `2026-02-30` → `2026-03-02`, `0000-00-00` → `-0001-11-30`, `25:00:00` → next day `01:00`). A `$parsed === false` check alone would let all of those through. Fractional seconds are matched and discarded; offset-bearing values (`Z`, `+02:00`) and the ISO `T` separator are rejected rather than assumed to mean UTC — the accept-set is exactly what the APIs emit.
  - **`ts` and `dateTime` are null together for date-only values**, and `date` is always populated. `dateTime` deliberately does **not** fall back to `date`: `strtotime($dt->dateTime)` on a fallback would return midnight UTC — precisely the fictitious instant `ts === null` exists to refuse. Null makes it fail loudly (`strtotime(null)` is a TypeError on PHP 8.1+). `tz` stays `"UTC"` even for date-only values: it describes the source *declaration*, not an instant. `castDate()`'s companion `tzAbbr` field is **not** carried over — there it held the abbreviation *at that instant* (`CET`/`CEST`), a distinction that cannot exist in a UTC-only type whose zone id and abbreviation are the same string and which has no DST, so it would duplicate `tz` in every value forever. (Ref: RSRMID-2318; localization split to RSRMID-2916.)
  - **Separator tolerance, both sides consistent (RSRMID-2926).** `PATTERN` accepts `-` (CNR) or `/` (IBS/Moniker actually send `2030/07/17`, not `2030-07-17` as an earlier revision of this note assumed) via a captured `sep` group plus a `\k<sep>` backreference, so `2026-02/20` and `2026/02-20` are both still rejected — the parser stays as strict about shape as before, just over a wider accept-set. `$date`/`$dateTime` always emit `-`: the matched date is normalised to `-` before it reaches `createFromFormat()`, so the struct's shape never depends on which brand sent it. This is still a parser, not a formatter — no new public method was added for it.
  - **`$raw` exists because the new accessors close the gap that used to guarantee the caller still had it (RSRMID-2926).** Before `getDateTimeByKey()`/`getDateTimeByIndex()`, the only way to obtain an `ApiDateTime` was `ApiDateTime::tryFrom($hash["paiduntil"])`, so a caller wanting the original string necessarily still held it alongside the parsed value — there was nothing to add. The accessor removes that: the raw value never passes through the integrator's own code, and recovering it afterwards means a second `getDataByKey()`/`getDataByIndex()` lookup plus a re-narrow, exactly the double work the accessor exists to eliminate. `$raw` is also the only place the fractional-second precision `$dateTime` discards survives (`"2026-07-25 07:46:34.813"` keeps `.813` in `$raw`). It is populated from the constructor's `$value` argument at both `from()` call sites — never from the separator-normalised subject — and is display/logging/round-trip only: comparing or sorting on `$raw` reintroduces exactly the separator bug `$date`'s ISO normalisation exists to prevent (`"2026/02/20"` sorts wrong against `"2026-03-01"` as plain strings). No getter, no `withRaw()` — one readonly property, nothing else.
  - **`Record`/`Column` gained one opt-in accessor each, not a shared helper.** `getDateTimeByKey()`/`getDateTimeByIndex()` are each a one-line narrowing over the existing accessor (`is_string($v) ? ApiDateTime::tryFrom($v) : null`), declared on both the class and its interface. The line is duplicated rather than factored into a shared trait/function: `Record` and `Column` have no composition relationship (see the RSRMID-2923 collapse above), so sharing one line would either invent a relationship that does not exist or add an indirection with nothing behind it. Both interface declarations widen the public contract — a consumer implementing `RecordInterface`/`ColumnInterface` directly must add the method — which is what makes this change breaking (RSRMID-2926, v28.0.0) independent of the separator change. The date accessor is **`CNIC\Column`-only**; `CNIC\CNR\Column` gained nothing, guarded by the existing `RecordColumnSeamTest::testCnrColumnNarrowsNothingButGetDataByIndex`.
  - **The IBS date-separator rewrite is deleted, not guarded (RSRMID-2926).** `src/IBS/ResponseParser.php` used to `array_walk_recursive()` over the decoded result and rewrite `/` to `-` in any string value whose key matched `/(date|paiduntil|expiration)$/i` — the only place in `src/` that mutated raw response data. It was also over-broad: a value like `n/a` under an `updatedate` key came back as `n-a`, corruption unrelated to any date. Deleting it needed **no** guard test: re-adding the rewrite is not behaviour-preserving (it changes `getHash()`/`getPlain()`/`getListHash()` output for every IBS/Moniker date field), so the ordinary `ResponseParserTest`/`ResponseTest`/`RecordTest`/`ColumnTest` assertions that now expect `/` verbatim already catch a regression — unlike the structural decisions above, where a green behavioural suite proves nothing.
  - **The interface declarations are protected by `#[\Override]`, not by a test.** Dropping `getDateTimeByKey()`/`getDateTimeByIndex()` from `RecordInterface`/`ColumnInterface` while leaving them on `Record`/`Column` would be behaviour-preserving for the entire suite — every test uses the concrete classes, and `RecordColumnSeamTest` is the only file that even names the interfaces — which by this repo's own criteria would normally demand a guard test. It needs none: both implementations carry `#[\Override]`, so removing the interface declaration is a declaration-time fatal (PHPStan and Psalm flag it too) rather than a silent behaviour change only a runtime test could catch. That is also why no `*SeamTest.php` was added for these two methods — but it means stripping `#[\Override]` from either implementation would silently remove the only thing protecting the interface declaration.
- **Failures throw from one hierarchy, and growing it is not a breaking change (RSRMID-2895).** Every exception the SDK raises extends `CNIC\Exception\CnicException`, which extends `\Exception`. The existing types each cover a distinct failure mode and should be reused rather than duplicated: `UnsupportedFeatureException` (a capability this platform or response does not have — and since RSRMID-2919 also a cURL option or HTTP header the transport owns), `PaginationException` (list-pagination misuse), `InvalidConfigurationException` (a configuration value out of the supported range, e.g. a negative socket timeout — added in RSRMID-2919), `InvalidDateTimeException`.
  - **The hierarchy is additive by construction, which is the point.** Because every class ultimately extends `\Exception`, existing `catch (\Exception)` consumer code keeps working when a new subclass appears, so introducing or extending it needs **no** `BREAKING CHANGE:` footer and no major bump. That is what makes "add a subclass for a genuinely new failure mode" the cheap option and a bare `\Exception` the expensive one — the bare throw is indistinguishable from a runtime bug at the call site and cannot be caught selectively ever after.
  - **Do not create parallel ad-hoc exception types outside `CNIC\Exception`.** The failure modes are the SDK's public vocabulary; a type declared next to the code that throws it is invisible to a consumer writing catch blocks against the namespace.
  - Related policy, recorded where it was decided: a capability the platform cannot honour is answered by **absence** first, a throw second, and never a no-op — see the RSRMID-2920 session-seam entry.
